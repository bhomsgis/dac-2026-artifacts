// The original assertion fails because is_req_waiting_d is a combinational signal updated in the same cycle as current_state, but the req.valid signals are inputs sampled in the current cycle. The assertion checks is_req_waiting_d against the current req.valid signals, but is_req_waiting_d is assigned based on the previous cycle's req.valid signals due to the state machine update. Therefore, the assertion should check is_req_waiting_q (registered) against the previous cycle's req.valid signals when current_state is IDLE in the previous cycle.  
// The proposed fix is to use a next-cycle assertion (|=>) with precondition current_state == IDLE and postcondition that is_req_waiting_q equals the AND of the req.valid signals sampled in the previous cycle ($past). This matches the pipeline behavior where is_req_waiting_q is updated at the clock edge after the req.valid signals are sampled.  
as__IsReqWaitingSetOnlyWhenBothReqValid: assert property((ptw_arb.current_state == ptw_arb.IDLE) |=> (ptw_arb.is_req_waiting_q == ($past(dtlb_ptw_comm_i.req.valid) && $past(itlb_ptw_comm_i.req.valid))));
